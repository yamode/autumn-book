# autumn-book アーキテクチャ設計メモ

星野リゾートの「施設サイト → 全国マップ空室検索 → 予約エンジン → 会員マイページ → ブランド切替」の動線を、山人（autumn）向けに落とし込んだ外部顧客向けプラットフォームの設計方針。

---

## 1. 全体像

既存リポは **従業員（内部）視点**の3リポ構造。

| リポ | 視点 | 対象ユーザー |
|------|------|------------|
| `autumn-rms` | 内部 | 従業員 |
| `autumn-pms` | 内部 | 従業員 |
| `autumn-order` | 内部 | 従業員 |
| **`autumn-book`（新設）** | **外部** | **お客様** |

→ 外部接点は **`autumn-book` として新規モノレポで立てる**。既存3リポとは統合しない。

### 判断軸：なぜ新リポ（既存と統合しない）か

ライフサイクル・デプロイ単位・対象ユーザーが既存3リポと全て異なるため。

- **対象が外部** — 不特定多数のお客様。認証方式・セキュリティ境界・公開範囲が社内ツールと根本的に別。同居させるとRLSやデプロイ設定の事故リスクが上がる。
- **デプロイ先・SLAが別** — 顧客向けは可用性・表示速度・SEO最優先（Cloudflare Pages等のエッジ配信想定）。社内ツールと要件が噛み合わない。
- **変更頻度・リリース判断が別** — 顧客UIは頻繁に更新、社内RMS/PMSは慎重にリリースしたい。CI・レビュー粒度が合わない。

星野リゾートも社内システムと顧客向けFleBOLは別基盤として扱われており、この線引きと一致する。

---

## 2. 3層アーキテクチャ

| 層 | 技術 | 役割 |
|----|------|------|
| Layer 1：フロント（表示層） | SvelteKit | 全ブランド・全施設・予約・会員を単一アプリで処理。URLルーティングで切替 |
| Layer 2：API／ロジック層 | SvelteKit server routes + Supabase Edge Functions | 空室検索・料金計算・予約確定・会員認証を集約。FileMaker PMSと双方向同期 |
| Layer 3：データ層 | Supabase (PostgreSQL) | 全ブランド・全施設の在庫・予約・会員を中央集権で保持 |

当面は FileMaker を在庫の正としつつ、Supabase を「直販の窓口＋全社横断ビュー」とする（Option A と整合）。

---

## 3. URLルーティング（星野リゾート踏襲）

施設HPを「独立サイト」ではなく「同じシステムの入口」として扱う。

```
autumn.jp/                       … 全体ポータル（ブランド一覧・全国マップ空室検索）
autumn.jp/[brand]/               … ブランドトップ（宿泊／飲食など）
autumn.jp/[brand]/[facility]/    … 施設ページ
autumn.jp/booking/...            … 予約エンジン（共通）
autumn.jp/account/...            … 会員マイページ（共通）
```

**ポイント：「ブランド」をデータとして持つ。** 宿泊も飲食店も `brands` テーブルの1レコードに過ぎず、`type`列（`lodging` / `restaurant` / `sauna` 等）で表示テンプレートを出し分ける。
→ ブランド追加＝コード追加ではなく**データ追加**になる（星野リゾートの界・リゾナーレ・OMO… を増やせる構造）。

---

## 4. データモデルの骨格

```
brands           ブランド（山人/飲食/サウナ…）   type, theme, logo
  └ facilities   施設                            brand_id, lat, lng, prefecture
       └ room_types / menu_items 等             facility_id（typeで分岐）
            └ inventory / availability          日次在庫
reservations     予約（全ブランド横断）           facility_id, member_id, status
members          会員（全ブランド共通の1ID）      ← マイページの中心
  └ member_reservations / points / profile
```

**会員は「ブランドごと」ではなく全社で1ID。** 山人で泊まった人が系列飲食店も同じログインで予約でき、ポイントも共通になる（FleBOLの会員統合と同思想）。

---

## 5. 顧客動線

```
[施設ページ] ──"空室を見る"──▶ [全国マップ空室検索]
                                    │ 日付・人数で全施設の空きを同時表示
                                    ▼
                              [予約エンジン]  ◀── 未ログインでも進める
                                    │ カート（複数泊・複数施設OK）
                                    ▼
                              [会員ログイン/ゲスト] ──▶ 確定 ──▶ [マイページ]
```

予約の変更（日程・人数・部屋タイプ）は、最初から `reservations.status` と変更履歴を持たせておけば後付けで実現できる（星野リゾートが問い合わせの約4割を占めた変更要望に対しオンライン変更機能を実装した点を踏襲）。

---

## 6. autumn-book の内部構成（モノレポ）

```
autumn-book/
├─ apps/
│  └─ web/                SvelteKit本体（施設サイト→マップ空室→予約→マイページ→ブランド切替）
├─ packages/
│  ├─ core/               料金・在庫ロジック（純粋関数）
│  └─ ui/                 ブランド共通コンポーネント
├─ supabase/              顧客向けスキーマ・edge functions
│  └─ functions/
├─ pnpm-workspace.yaml
└─ turbo.json             （任意：ビルドキャッシュ）
```

- pnpm workspace でパッケージ間を `workspace:*` 参照。
- `supabase/` はルート直下に置く（Supabase CLIの期待挙動に合わせる）。生成型は `packages/` 側に置く折衷案。
- worktree運用と相性良好（予約エンジンと会員機能を並行作業しても同じ型を参照）。

### なぜモノレポか（リポを分けないか）

山人の規模（少人数開発＋Claude Code）では、リポ分割のメリット（チーム独立・権限分離）よりデメリット（型・スキーマの二重管理、横断変更で複数PR、CI重複）が上回る。フロント・API・DBスキーマ・型が密結合する1プロダクトなので束ねる。

---

## 7. 最重要論点：DBの共有方法

`autumn-book` の予約は最終的に `autumn-pms` の在庫・予約データと繋がる必要がある。**リポは分けてもデータ層は分断できない。**

| 選択肢 | 内容 | 評価 |
|--------|------|------|
| **1. 同一Supabaseプロジェクト共有** | book は顧客向けスキーマ／RLSだけ持つ。予約は共通 `reservations` に書く | ◎ 最もシンプル。整合性が自然に取れる |
| 2. 別Supabaseプロジェクト＋同期 | 顧客影響と社内を物理分離 | △ 同期層が重い |
| 3. スキーマ定義リポを別出し（`autumn-db`） | book/pms/rms が型を共有 | ○ 型は1ソース化できるが運用増 |

### 推奨：選択肢1（同一プロジェクト＋スキーマ／RLS分離）

- `autumn-pms` と同じSupabaseを見る。
- 顧客がアクセスできる範囲は **RLSで厳格に絞る**。
- 型の共有は、将来 `autumn-db` パッケージを private npm or git submodule で切り出し、4リポで共有する余地を残す段階設計。

---

## まとめ（結論）

1. **`autumn-book` を新規モノレポで立てる**
2. **既存3リポ（rms/pms/order）とは統合しない**
3. **DBは `autumn-pms` と同一Supabaseをスキーマ・RLSで分離共有**
4. **ブランド・施設・会員はデータ駆動**（テンプレートを `type` で出し分け、会員は全社1ID）
