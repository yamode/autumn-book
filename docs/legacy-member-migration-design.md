# 旧会員（tripla）の会員移行 — 設計書 v2（レビュー用）

- 作成: 2026-11-19（v1 = Book v0.289.0 / autumn-shared `20261119115140` の実装を見直したもの）
- 状態: **レビュー中**。v1 の入口と DB は本番に入っているが、旧会員の一覧は空（取り込み前）。Book はローンチ（2026-11-30）まで一般公開前（503）なので、外部から実行できない
- 根拠: 世界の事例・指針の調査（§9 出典）と、v1 の自己点検（§2）

## 1. 目的と前提

- 以前の予約システム tripla の会員が、Book の会員に移れるようにする。引き継ぐのは**登録内容（氏名・カナ・電話）**と、**PMS に残る過去の公式・直販の利用実績（会員ランク）**
- tripla から受け取れるのは会員一覧の CSV だけ（**パスワードのハッシュは受け取れない**）→ 「一括取込＋本人が受け取る（claim）」型にする（Shopify の招待方式・Auth0 の一括取込と同じ考え方）
- 会員ランクは、会員に紐づく PMS 顧客（`core.guests`）の**通算の公式・直販の利用回数・泊数**（`book._member_lifetime_stays`。OTA は数えない）で決まる
- マイページは、紐づく PMS 顧客の**プロフィール（氏名・電話・住所・生年月日）**と、その顧客の Book の予約を表示する（`book.my_profile` / `my_reservations`）
  → **紐づけを誤ると、他人の個人情報と予約を見せることになる**。これが本件の最大の危険

## 2. v1 の自己点検で見つかった問題

| # | 問題 | 重さ | 対策（§4 以降） |
|---|---|---|---|
| P1 | 「電話＋氏名」の一致で **PMS 顧客に自動で紐づける**。家族・旅行会社・会社での電話の共用、番号の再割り当て（日本では解約番号の半数以上が 3 年以内に再割り当て）で誤る。誤るとマイページに他人の住所・生年月日・予約が出る | 致命 | 自動確定はメール一致（＋氏名の整合）だけ。電話＋氏名は「候補」にして職員が確かめる |
| P2 | 完了時に `update_my_profile_contact` を呼び、**PMS の顧客マスタ（住所・生年月日・氏名・電話）を tripla の古い値で上書き**する。誤照合なら他人の顧客情報を壊す | 致命 | PMS 顧客は一切更新しない。住所・生年月日は引き継がない（取り込みもしない） |
| P3 | 同じメールの Auth ユーザーが**スタッフ・管理者**だと、公開側の流れでそのアカウントにパスワードを設定してしまう（管理画面のログインの決まりを迂回） | 高 | admin / staff の Auth ユーザーには移行させない（一般の案内と同じ表示で止める） |
| P4 | リンクの URL を **`event.url.origin`（Host ヘッダ由来）** で組み立てている（OWASP: Host ヘッダを信用しない） | 中 | 固定のドメイン（`BOOK_SITE_BASE_URL`）で組み立てる |
| P5 | 対象のときだけメールを送るので、**応答時間の差で会員かどうかが分かりうる** | 中 | 送信を応答の後に回す（`platform.ctx.waitUntil`）。処理時間をそろえる |
| P6 | リンク先で以前の電話番号をそのまま表示。リンクが転送されると見える | 低〜中 | 電話は下 4 桁以外を伏せる（入力し直してもらう）。リンクは 1 回限り・短い期限 |
| P7 | 完了の**通知メールが無い**（NIST・OWASP は復旧・再設定の完了通知を求める） | 中 | 完了通知メール（「心当たりがなければ連絡を」） |
| P8 | メール配信の同意を**既定でオン**。特定電子メール法上、tripla での同意の記録が無ければ取り直しが要る | 中 | 既定はオフ。CSV に同意の記録（日時）がある人だけ、その旨を表示して既定オン |
| P9 | 取り込んだ一覧（`raw` に元の行をすべて保存）を**消す期限が無い** | 中 | 取り込むのは必要な列だけ。受付期間の終了後に削除し、削除日を記録 |
| P10 | 既に Book 会員のメールには何も送らないので、本人は「届かない」と迷う | 低 | 既存会員には「既に会員です。ログインしてください」のメールを送る（画面は同じ） |

## 3. 世界の事例から採る教訓（要約）

- **Marriott–SPG（2018）**: 統合後に実績・ポイントが欠け、「欠けを見つけるのは会員任せ」と批判された → 移行後に本人がランクの根拠（通算回数）を見られるようにし、問い合わせ窓口と手順書を用意する
- **Alaska–Hawaiian（2025）**: 事前に連携しなかった会員に別アカウントができ、重複の解消に電話が必要になった → 「同じメールの Book 会員がいれば、新しく作らず既存に結び付ける」
- **IHG・Hilton**: 移行やキャンペーンの時期に乗っ取り（メール変更→ポイント使用）が多発 → 回数制限・完了通知、メール変更とポイント利用の通知
- **Cloudbeds・Mews（PMS）**: 名寄せは高信頼の一致だけ自動、それ以外は職員が見比べて決める。手動の統合は解除できる → 本設計の照合方針の根拠
- **フィッシング**: 移行案内を装う詐欺が実際に起きている → 一斉案内にはリンクを載せず、本人がサイトから始める流れにする

## 4. 設計 v2

### 4.1 取り込み（職員・Claude が行う）

- 取り込む列は**最小限**: メール、氏名（姓・名）、カナ（姓・名）、電話、tripla の会員 ID、登録日、メール配信の同意（あれば日時）。**住所・生年月日・性別は取り込まない**
- 保存先は `book.legacy_members`（service_role 専用・RLS 有効でポリシー無し）。`raw` は廃止（元の CSV は取り込み後に Dropbox から消す）
- 取り込み時に PMS 顧客と照合（§4.2）。結果は件数だけを報告し、要確認の一覧は管理画面で見る

### 4.2 PMS 顧客との照合

| 区分 | 条件 | 扱い |
|---|---|---|
| **auto（自動で確定）** | ① メールが PMS 顧客のメール（`core.guests.email` または `core.guest_identities` の email）と一致し、**候補がちょうど 1 人**、かつ ② その顧客の氏名（漢字かカナ）が旧会員の氏名と一致、または顧客側に氏名が無い | 移行の完了時にその顧客に紐づける（ランクに反映） |
| **candidate（候補）** | メールは一致するが氏名が食い違う／電話＋氏名が一致する／候補が複数 | **自動では紐づけない**。移行の完了時は**新しい顧客**として会員にする（ランクは入会時のまま）。管理画面の「要確認」に出し、職員が見比べて承認したときだけ紐づけ直す |
| none | 一致なし | 新しい顧客として会員にする |

- 個人以外の顧客（`guest_type <> 'individual'`）・旅行会社の名前の顧客は対象外
- 職員の承認による紐づけ直し（candidate → 確定）は、`book.members.guest_id` を差し替え、監査記録（`book.admin_audit_logs`）に残す。**解除できる**（元の顧客に戻す）
- PMS の顧客マスタ（`core.guests`）は**一切更新しない**。紐づけは `core.guest_identities` に email を 1 行足す（auto のとき）か、`members.guest_id` の差し替え（職員の承認）だけ

### 4.3 本人の手続き

1. `/auth/migrate` でメールを入力（Turnstile・回数制限: IP 10 分 10 回／メール 1 時間 3 回／DB 側でメール 1 日 5 通）
2. 画面は**常に同じ文言**。送信は応答の後（`waitUntil`）に行い、処理時間をそろえる
   - 旧会員の一覧にあり・未移行・Auth ユーザーが会員でもスタッフでもない → 移行リンクのメール
   - 既に Book 会員 → 「既に会員です。ログインはこちら」のメール（リンクはログイン画面）
   - それ以外（一覧に無い・スタッフ・回数超過）→ 何も送らない
3. リンク: 32 バイト乱数・DB はハッシュのみ・**1 回限り**・新しく発行すると古いものは無効・期限 **2 時間**（再送は簡単）・URL は固定ドメイン・`no-store`・`no-referrer`・`noindex`
4. リンク先: 氏名・カナは入力済み（以前の内容）、電話は下 4 桁だけ見せて入力し直してもらう。新しいパスワード（12 文字以上・72 バイト以内）、プライバシーポリシーへの同意（必須）、メール配信（既定オフ。tripla での同意の記録がある人だけ既定オン）
5. 完了: Auth ユーザーを作る（既にあって会員でなくスタッフでもなければ、そのアカウントにパスワードを設定）→ サインイン → 会員登録（auto なら照合済みの顧客に名寄せ）→ 移行済みに記録 → **完了通知メール** → マイページ
6. 完了後、同じリンクは無効

### 4.4 告知と運用

- 一斉の告知メール（tripla 会員宛て）を送る場合は**リンクを載せない**（「公式サイトのログイン画面の『旧会員の方』から」と書く）。「パスワードをメールで聞くことはない」と明記
- HP・Book のログイン画面・会員登録画面に「旧会員の方（会員移行）」の入口
- 受付期間を決める（案: 2027-05-31 まで）。期間後は入口を外し、通常の新規登録へ案内。未移行の行は削除し、削除日を記録
- 問い合わせの手順書: メールが使えなくなった人は、職員が本人確認（予約番号・電話・住所の照合）してから手作業で移す
- 計測: 一覧の人数、リンク送信数、完了数、期限切れ、auto / candidate / none の件数、要確認の処理数

### 4.5 法令・規約（オーナーの確認が要る）

- **tripla の役割**: 山人の**委託先**として会員データを扱っていたなら、データを山人に戻すのは第三者提供にあたらない。tripla が**自社の会員**として管理していたなら第三者提供になり、原則として本人の同意が要る → **tripla との契約・規約で確認**（確認できるまで取り込まない）
- **利用目的**: 「過去の宿泊実績を会員ランクに使う」ことが、公表しているプライバシーポリシーの利用目的に入っているか確認。入っていなければ改定・公表
- **メール配信**: tripla での同意の記録（日時・表示）が CSV に無ければ、移行の手続きで取り直す（既定オフ）
- **削除**: 受付期間の後、未移行の旧会員データを削除（個人情報保護法の努力義務）

## 5. ポイント

- tripla のポイントは引き継がない（2026-11-19 決定）。入会ボーナスは通常どおり付く。案内文で「以前のポイントは引き継がれません」と明記するかは要決定

## 10. Fable のレビュー（2026-11-19）と v3 の方針

**結論: v2 は方向は正しいが、このままでは実装不可。** 主要な指摘はコードと照合して正しいことを確認した。

| # | 指摘 | v3 での対応 |
|---|---|---|
| C1 | 紐づけを決めているのは `register_member`。確認済みメールが `guest_identities` にあれば**氏名を見ずに**その顧客へ紐づける（`20261021003205` 480-485 行）ため、v2 の auto / candidate が効かない。prepare が別トランザクションで identity だけが残りうる | 移行では `register_member` を使わず、紐づけ先（`p_guest_id`、null なら必ず新規顧客）を明示する service_role 専用の RPC を作る。prepare・会員作成・complete を 1 トランザクションに |
| C2 | auto の条件が弱い（氏名の無い顧客でも確定・既に会員が付いた顧客にも確定し入会ボーナスが二重）。氏名の正規化が弱い（半角カナ・ひらがな等） | auto = メール一致 1 人 ∧ 氏名一致（無しは candidate）∧ その顧客に現役会員なし ∧ 本人が入力し直した電話が一致。auto 直後も住所・生年月日は本人の確認まで伏せる。正規化を強める |
| C3 | 既存の Auth ユーザー（退会者・LINE 連携・パスキー・TOTP）にリンク経由でパスワードを設定してしまう | 既存の Auth ユーザーがいれば、リンクではパスワードを設定しない。通常のログイン（メールのコード）の後に、ログインした状態で「旧会員の実績を引き継ぐ」へ。退会者の再入会の方針を決める |
| H1 | 先に通常登録した旧会員が引き継げない（`already_member` で止まる） | 通常の登録・ログインの後にも同じ照合・引き継ぎを通す（マイページから「以前の会員の実績を引き継ぐ」） |
| H2 | ランクの再計算が全会員対象（`skip locked` で同時実行時に漏れる）。ランクは上がる方向にしか変わらず、紐づけを解除しても戻らない | 本人 1 人だけの再計算関数。解除時は監査記録の変更前ランクへ戻す |
| H3 | メール単位の上限超過で 429（本人を締め出せる・v2 と食い違い）。全体の上限が無い。KV は読めないと通す | 超過も同じ画面のまま送らない。全体の上限を足す。DB 側の上限を主にする |
| H4 | 会員がメールを変えても古いメールの identity が残り、後でそのメールを得た他人が通常登録すると同じ顧客に紐づく | `register_member` に「現役会員がいる顧客には名寄せしない」。メール変更時に identity を付け替える（既存の不具合・移行と独立に直す） |
| M1 | トークンが URL のパスにある（解析タグに送られうる） | 着地時に HttpOnly Cookie へ移して URL から消す |
| M2 | complete が期限を見ていない | 期限も見る。「GET では消費せず POST の完了で消費」を明記 |
| M3 | 同意の記録が無い・メール配信が既定オン | 同意の日時・文言の版を保存。既定オフ |
| M4 | 不要な列（zip / address / birthdate / gender / raw）が残る | DROP |
| M5 | Turnstile の hostname も `event.url.hostname`。`*.pages.dev` からも入れる | 固定ドメイン。`*.pages.dev` では入口を閉じる |
| M6 | 法令 | tripla に契約主体・同意の文言・退会者／配信停止者の除外を確認。利用目的に「PMS の宿泊履歴との名寄せとランクの算定」を明記。開示・削除の対象に旧会員の一覧を含める |
| Low | リンクの期限は 24 時間でよい（GET は状態を変えず、守りは電話の一致と完了通知で足りる）。受付期間は 3 か月＋延長 | 採用（§7 の案を更新） |

**進め方（採用）**
1. v1 の入口は設定（`LEGACY_MEMBER_MIGRATION`）で**閉じた**（v0.289.1）。`/auth/migrate` は「準備中」、ログイン・登録画面のリンクも出さない

4. CSV の取り込みは、tripla との契約（委託か第三者提供か）を確かめた後

| High-2 | 移行の完了で自動で紐づけたものは `previous_guest_id` が無く、解除できない。職員の一覧にも出ない | 完了で紐づけたときも、本人が入力した内容で戻し先の顧客を作り `previous_guest_id`・`previous_rank='standard'` に残す。一覧に linked を全件出す |
| High-3 | 職員の一覧に、本人が手続きで入力した氏名・電話が出ない（食い違いに気づけない） | 一覧に `entered_name`・`entered_kana`・`entered_phone` を足し、管理画面で食い違いを赤字にする。食い違えば **PMS の電話番号へ宿から電話して確かめてから**紐づける、と画面と手順書に書いた |
| Medium-1 | メール配信が、以前の同意があると既定オン | 常に既定オフ（改めて選んでもらう）→ 2026-11-22 ユーザー指示で既定オンに変更（会員登録画面と同じ・外せば受け取らない） |
| Medium-2 | 完了の途中で失敗するとアカウントを消すが、会員ができていても消してしまう（応答の取りこぼし） | 会員の行があれば消さない。完了メールの失敗では巻き戻さない |
| Medium-3 | 引き継ぎの案内が会員でない人にも出る。「login」の案内に会員登録の一言が無い | `legacy_member_claimable` は現役会員だけ。案内メール・画面に「会員登録がまだなら続けて会員登録」を足した |
| Medium-5 | 「既に会員です」等の案内メールは DB 側の上限を数えず、一覧に無いメールにも送れる | 一覧にあるメールだけに送り、どの種類も 1 日 5 通の上限で数える。職員のアカウントには送らない |
| Low | 入口の除外（`*.pages.dev`）が抜けやすい／職員が候補以外の顧客に紐づけられる／identity の大文字小文字 | 許可リスト（book.yamado.app と開発中の手元だけ）／候補（`candidate_guest_ids`・`matched_guest_id`）だけ／付け替えは大文字小文字を区別しない |
| Medium-4 | 確認待ちの個人データ・移行済みの行をいつまで残すか | 開けてから 1〜2 週で決める（手順書 6.） |

**以前からある別の課題（移行と独立）**: 予約の確定で、受信を確かめていないメールにも identity を足している／`register_member` は一般にメールで氏名を見ずに名寄せする。→ 別に検討する。
